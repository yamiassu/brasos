# extension

The BrasOS extension for the real browser (`brasos.browser`, dev image only). When you install a site as an app in that browser, it asks BrasOS to add the app too, and BrasOS shows its own install prompt.

- **`ext/`** is the extension itself (Manifest V3, loaded unpacked by the browser's command line in `packages/compositor/browser.nix`; the image writes `config.js` with the host's address). `content.js` runs in every page and does nothing until the browser fires `appinstalled` (or the toolbar button, "Add this site to BrasOS", asks); it then sends the page's manifest address to the worker. `background.js` posts `{ manifestUrl }` to `POST /os/apps/requests` and shows a badge (✓ sent, ! failed or no manifest). `core.js` checks the address (plain http(s), at most 2048 characters).
- **It asks for very little**: no `permissions`, host access only to `http://localhost/*`, no web-accessible resources, nothing a web page can message. A test checks this.
- **Identity**: the manifest carries a public key, which fixes the extension id (`src/index.ts`, `EXTENSION_ID`; a test checks they match). The private half was thrown away: nothing is ever signed, because the extension is loaded unpacked. The host recognises the extension by its exact origin (`chrome-extension://<id>`), which a web page can't send and no other extension has.
- **What the host does with it** (`packages/registry`): the extension holds one capability, `apps.request`, and can do nothing else (it can't read the queue, inspect, install or touch files). A request is queued in memory (at most 20, 15 minutes, one per manifest address), audited as `apps.request` with the site's name only. The shell (the only reader, `apps.install`) polls the queue, shows the install prompt for the first request and then dismisses it. **Asking installs nothing**: the person grants permissions and chooses where the app runs.
- **Where an installed app runs** (`runIn` on the app): `brasos` (default) is a BrasOS window on the web gateway, sandboxed; `browser` is an app window of the real browser (`--app=<address>`, the `webapp` native app: same profile, not isolated, no BrasOS permissions), offered only where the real browser exists.
- The hardened package denies `apps.request`, and the real browser (and so the extension) never ships in it.
- Limits: it needs the browser to load an unpacked extension from the command line and to fire `appinstalled`; if a Chromium build stops allowing the first, the image has to load it another way. A site the browser installs without a manifest link can't be added (the toolbar button says so with a !).
